# Wire-Format Protocol Specification — v0 (Draft)

Status: **draft**, pending solution-architect and security-engineer sign-off (§9). This is the
Phase 0 "protocol spec v0 draft" deliverable from `PLAN.md` §7 / §5 ("Protocol portability").
Schemas referenced here live in `spec/proto/v0/*.proto` and are the source of truth for field
numbers and types; this document is the rationale and the rules that govern how those schemas
are used and evolved.

This spec does not re-derive or restate the Signal Protocol itself. X3DH/PQXDH, the Double
Ratchet, and Sender Keys are taken as given from upstream `libsignal`, exactly as
`docs/threat-model.md` does. What this spec defines is the layer **around** `libsignal`: how its
opaque ciphertext is framed, addressed, and routed between a sender, the transport (direct P2P or
a relay), and a recipient — the "Protocol layer" in `docs/threat-model.md` §4.2.

---

## 1. Scope

In scope for v0:
- The outer `Envelope` that every message, receipt, and Sender Key distribution travels in.
- The Sealed Sender wrapper structure.
- Prekey bundle and DHT discovery record shapes used for asynchronous session setup.
- The versioning and compatibility rules that govern all of the above.

Out of scope for v0 (tracked separately, not silently assumed):
- The internal wire format of `libsignal`'s own messages (`PreKeySignalMessage`,
  `SignalMessage`, `SenderKeyMessage`, `SenderKeyDistributionMessage`). Those are upstream
  `libsignal` types we treat as opaque bytes — see §4.
- Relay-to-relay or relay-to-DHT control protocols (fetch/store APIs, rate-limiting handshakes).
  This spec defines what a relay stores and forwards, not how a client talks to a specific
  relay's API — that is Phase 4 work (`PLAN.md` §7).
- Backup/export file format (`PLAN.md` §5, data portability) — a separate spec.
- Device-linking message shapes (`PLAN.md` §4) — drafted alongside the Phase 6 Multi-Device epic.
  The *semantics* of unlinking/revocation are defined in §8 and their wire shapes in §7.1.
- Actual `prost`/codegen wiring into `core/protocol` — this story is the spec draft only; wiring
  generated types into the Rust crate is separate implementation work so review of the wire
  format itself isn't coupled to a specific codegen toolchain choice.

## 2. Design Principles

1. **The envelope never inspects Signal Protocol ciphertext.** `Envelope.ciphertext` (and the
   `inner_ciphertext` it may wrap via Sealed Sender) is opaque bytes produced and consumed only
   by `libsignal`. This protocol layer is not in the business of cryptography — it is in the
   business of addressing and framing, per `PLAN.md` §2 layer responsibilities.
2. **Routing metadata is the metadata budget, and it is itemized.** Every plaintext field on
   `Envelope` is something a relay or DHT peer can see (`docs/threat-model.md` §4.2,
   §6 "Summary: What Leaks Where"). A field is only added if something downstream actually needs
   it for routing or delivery; "might be useful later" is not sufficient justification for a
   field that a malicious relay can also read.
3. **Fail closed on the unknown.** Protobuf's forward-compatibility (unknown fields are
   preserved/ignored, not rejected) is necessary but not sufficient: an `EnvelopeType` a client
   doesn't recognize, or a `version` newer than it supports, MUST be treated as undeliverable to
   the application layer, never as a best-effort fallback to some default decoding. See §3.
4. **Sender identity and routing hints are never both plaintext at once for content messages.**
   `Envelope.sender` is unset whenever `ciphertext` is a Sealed-Sender-wrapped content message —
   see §5. This is enforced by convention in this draft; a follow-up story should turn it into a
   structural invariant (e.g. a oneof) once the surrounding session-management code exists to
   validate it meaningfully.

## 3. Versioning Policy

Two independent version numbers exist and must not be conflated:

- **`Envelope.version`** (`spec/proto/v0/envelope.proto`) — the wire version of this outer
  envelope format. This document defines version `0`.
- **The Signal Protocol session/ciphertext version** carried inside `libsignal`'s own serialized
  messages — entirely libsignal's concern, opaque to this layer (§1, §4).

Rules for v0:
- A v0 client sets `Envelope.version = 0` and MUST reject (fail closed, never best-effort parse)
  any envelope whose `version` it does not explicitly know how to handle.
- New fields within version `0` follow standard protobuf evolution: new fields get new field
  numbers, are optional in effect (proto3 scalar fields default to their zero value), and old
  clients ignore fields they don't recognize. This is "non-breaking" only in the wire-decoding
  sense — a v0 client still cannot act on semantics it doesn't understand.
- A **breaking** change (removing a field, changing a field's meaning, changing a field's type,
  or changing required behavior for an existing `EnvelopeType`) requires incrementing
  `Envelope.version` and a new dated entry in §10 (Changelog), not a silent edit of this document.
- This document and the `.proto` files it describes are versioned together. `spec/v0.md` and
  `spec/proto/v0/` will not change incompatibly once any client implements against them; the next
  incompatible revision is `spec/v1.md` / `spec/proto/v1/`, published alongside, not in place of,
  v0.
- "Published" (per `PLAN.md` §5, "Protocol portability") means: once this draft is signed off
  (§9) and a client ships against it, `spec/proto/v0/*.proto` is frozen. Independent
  implementations can rely on it not moving under them.

## 4. Mapping `EnvelopeType` to `libsignal` Message Types

| `EnvelopeType` | `ciphertext` / `inner_ciphertext` contains | Used for |
|---|---|---|
| `ENVELOPE_TYPE_PREKEY_MESSAGE` | `libsignal` `PreKeySignalMessage` | First message of a new X3DH/PQXDH session (`PLAN.md` §3) |
| `ENVELOPE_TYPE_CIPHERTEXT_MESSAGE` | `libsignal` `SignalMessage` | Double Ratchet message in an established 1:1 session |
| `ENVELOPE_TYPE_SENDER_KEY_MESSAGE` | `libsignal` `SenderKeyMessage` | Group message under an established Sender Key session (`PLAN.md` "Locked decisions") |
| `ENVELOPE_TYPE_SENDER_KEY_DISTRIBUTION` | `libsignal` `SenderKeyDistributionMessage` | Distributing/rotating a Sender Key to a group member |
| `ENVELOPE_TYPE_RECEIPT` | `libsignal` `SignalMessage` (a receipt is itself a Double-Ratchet-encrypted 1:1 message; only its decrypted application-layer content differs) | Delivery/read acknowledgement |

This layer never decodes the bytes in these columns; it routes them. The mapping exists so an
implementer knows which `libsignal` deserializer to hand the bytes to once `Envelope.type` and
Sealed Sender status (§5) identify which case applies.

## 5. Sealed Sender

`spec/proto/v0/sealed_sender.proto` defines `SealedSenderContent` — the structure of the data
that gets Sealed-Sender-encrypted by `libsignal`, not a structure that appears in plaintext on
the wire. When Sealed Sender is in effect for an envelope:

- `Envelope.sender` is unset.
- `Envelope.ciphertext` holds libsignal's sealed-sender-encrypted bytes, which decrypt (only by
  the intended recipient) to a `SealedSenderContent`.
- `SealedSenderContent.sender` is the real sender device address, `sender_certificate` is a
  short-lived self-signed certificate binding that address to the sender's identity key (no
  central CA exists in this design — `PLAN.md` §3), and `inner_ciphertext`/`inner_type` carry the
  actual `libsignal` message per §4.

Per `docs/threat-model.md` §4.1: this hides the sender field from anyone who handles the
envelope in transit, but it does **not** hide the sender's network identity (source IP / libp2p
peer ID) from a relay, and it provides no protection against a compromised recipient. Treat it as
a confidentiality control on one field, not a network-anonymity guarantee.

Sealed Sender is **not** used for `ENVELOPE_TYPE_SENDER_KEY_DISTRIBUTION` or
`ENVELOPE_TYPE_RECEIPT` in v0: group membership already discloses participants for the former,
and receipts travel inside an already-established 1:1 session where the recipient already knows
the sender by definition. Extending Sealed Sender to receipts is an open item (§7), not a gap
being silently accepted — receipts currently disclose `Envelope.sender` in plaintext to the relay
they transit, which is a real (if narrow) metadata leak relative to a normal message.

## 6. Prekeys and Discovery

`spec/proto/v0/prekey.proto` defines:

- `SignedPreKey` / `OneTimePreKey` / `PqPreKey` — the medium-term, one-time, and optional
  post-quantum components of a session-setup bundle, matching `PLAN.md` §3.
- `PreKeyBundle` — what a sender fetches to start a session with an offline device. Every
  signature in a fetched bundle **must** be verified against `identity_key` before use; per
  `docs/threat-model.md` §4.6, a DHT response is a hint, not a fact, until verified.
- `DiscoveryRecord` — what gets published to the DHT under a handle: one `PreKeyBundle` per
  linked device, signed as a set by the primary device so a malicious DHT peer can't splice in a
  rogue device's bundle (`docs/threat-model.md` §2, "Handle-squatter" and "Malicious DHT peer"
  adversaries). This signature does not, and cannot, defend against a primary device that is
  itself compromised — that adversary already holds the signing key by definition.

An empty `one_time_pre_keys` list is a valid, expected state (pool exhaustion under load), not an
error condition; see the field comment in `prekey.proto` and the corresponding risk entry in
`PLAN.md` §10 ("Offline prekey exhaustion").

## 7. Open Items Deferred Past v0

Tracked here so they are visible, not silently dropped:

- **Receipt metadata leak** (§5): `ENVELOPE_TYPE_RECEIPT` currently discloses `Envelope.sender`
  in plaintext to the relay. Revisit once Sealed Sender's certificate model is validated for the
  1:1 message case it already covers.
- **No padding/length-hiding.** `Envelope.ciphertext` length leaks approximate message size to
  every relay/DHT peer that handles it, consistent with the residual "traffic-analysis metadata"
  risk in `docs/threat-model.md` §6. Padding is explicitly a Phase 9 item (`PLAN.md` §7).
  Reserving a field for it now (e.g. a fixed-size padding blob) is deferred rather than guessed
  at speculatively in v0 — see Core Principles ("minimal footprint") in `CLAUDE.md`.
  - **Field-number reservation:** `Envelope` reserves no field for padding in v0. If a v1
    revision adds one, it must use a new field number (per §3) so v0 decoders that ignore
    unknown fields remain correct rather than misinterpreting padding bytes as something else.
- **Relay control-plane protocol** (§1): how a client authenticates to, queries, and pushes
  envelopes to a specific relay instance is not specified here. Phase 4 (`PLAN.md` §7) work.
- **`prost`/codegen wiring into `core/protocol`**: out of scope per §1; tracked as follow-up
  implementation work once this draft is signed off.
- **Primary-device revocation**: §8 defines revocation for a non-primary device. Revoking the
  primary device (the holder of the device-list signing authority) is not resolved here — it is
  the "compromised primary device" adversary in `docs/threat-model.md` §2 and needs its own
  design under the Multi-Device epic (`PLAN.md` Phase 6).

### 7.1 Device-list and discovery wire shapes (implemented)

Recorded here because it was previously deferred: the signed device list, the signed revocation
record, and the relay's discovery blob are now implemented. The shapes below are the ones in
`core/protocol/src/device_list.rs`, `core/protocol/src/fanout.rs`, and `relay/src/discovery.rs`.

A device list is `{account, version, entries}`:

- `account` — the account primary's serialized `IdentityKey`, exactly 33 bytes (one `0x05` type
  byte plus 32 key bytes). It is the key a peer verifies the list against.
- `version` — `u64`, at least 1. A peer accepts a list only if its version is **strictly** greater
  than the version it already holds, so a replayed same-version list is rejected.
- `entries` — 1..=256 devices, each `{device_id: u32, identity_key: 33 bytes,
  prekey_bundle: 1..=8192 bytes}`. Exactly one entry has `device_id == 0`: the primary device is
  itself a fan-out recipient. Device ids are unique within a list.

The primary signs the canonical encoding, which is domain-separated by the 18-byte ASCII prefix
`e2e:device-list:v1` and uses fixed-width big-endian integers throughout (`u64_be(version)`, then
length-prefixed `account` and `entries`). The signature is not part of the signed bytes: the
on-the-wire blob appends `u32_be(sig.len())` and the signature, and is at most 65536 bytes with no
trailing bytes.

A client publishes that serialized list as the discovery blob for the account's `recipient_id`
(`clients/web/src/discovery.ts` over `clients/web/src/relay_transport.ts`), which is why the relay
never needs to understand it.

Revocation has its own signed record (`SignedRevocation`, `core/protocol/src/fanout.rs`), so a peer
can verify a single removal without fetching a whole list. It carries the account binding (the
signing primary's serialized identity key), the revoked `device_id`, and the device-list `version`
the removal applies to. Its wire layout is self-delimiting: a 1-byte layout tag `0x02`, then
`u32_be(account.len())` + `account`, `u32_be(device_id)`, `u64_be(version)`, and
`u32_be(sig.len())` + signature. The signature covers the ASCII prefix `DR-2 device revocation v1`
followed by the account, device id, and version, so a revocation cannot be transplanted onto
another device or account. A revocation is accepted only at a version strictly greater than the
one already held, and re-revoking an already-revoked device is rejected.

The relay stores the published blob opaquely, under two WS ops:

- `publish_discovery` — writes the blob under a `recipient_id`. Capped at 65536 bytes inclusive (an
  oversize publish is rejected without touching the blob already stored), granted a 7-day TTL, and
  last write wins. Requires proof of work, and is rate limited.
- `lookup_discovery` — returns the stored blob without consuming it, so repeated lookups return the
  same bytes until the TTL expires. Rate limited.

The relay never parses, decodes, or verifies the blob; it enforces only the size cap and the TTL.

### 7.2 Group device fan-out (implemented)

Recorded here because it was previously deferred: a group message now reaches every recipient
*device*, not just each member's primary. The behaviour below is the one in
`clients/web/src/group_recipients.ts`, `clients/web/src/group_roster.ts`, and
`clients/web/src/useGroupConversation.ts`.

- **One envelope per recipient device.** `ENVELOPE_TYPE_SENDER_KEY_MESSAGE` still addresses a
  single `DeviceAddress` per envelope. A group send therefore emits one envelope per recipient
  device, resolved from each member's verified signed device list (§7.1), plus the sender's own
  other devices.
- **Identical ciphertext.** The sender encrypts once. `GroupSession::encrypt_as` seals the
  per-message key separately to every identity key in the sender's roster, and the resulting
  ciphertext bytes are delivered unchanged to every device mailbox. Nothing is re-encrypted or
  re-persisted per device; the ratchet advances once per logical message.
- **Address scheme.** Device `0` (the primary) is addressed at the bare account handle; each
  linked device at `${accountHandle}:${deviceId}`. An account handle may not contain `:`, so the
  two forms cannot collide and one account's handle cannot shadow another's linked-device
  mailbox.
- **Device keys in the sender roster.** The roster holds recipient *device* identity keys (device
  0's key is the account's own identity key; each linked device has its own), and is reconciled
  against the resolved devices on every send: every recipient device key is present exactly once,
  and a key that has stopped being a recipient (a removed member, or a device its account revoked)
  is evicted. A handle whose device list could not be resolved this round is left alone rather
  than evicted, because a null lookup is not evidence of revocation.
- **The 255-recipient limit counts devices.** The wire format caps a group envelope at 255
  wrapper recipients, and each recipient is a device. A send whose resolved device count exceeds
  255 is refused before anything is encrypted, persisted, or sent, rather than producing an
  envelope no recipient can decode.
- **Bare-handle fallback.** A member with no published device list — or whose list fails
  verification or lookup — is addressed at its bare handle only, so its primary still receives
  while its linked devices do not. The gap is reported to the caller rather than silently
  dropped, and one member's failure never fails the whole send.
- **Attribution limitation.** Sender attribution infers the sender as the one known member whose
  account identity key is absent from the wrapper roster. The roster is now device-level, so that
  inference is not guaranteed to be unique in a multi-device group. When it is not, the receiver
  records no attribution rather than guessing: a received group message may show no sender, but it
  is never attributed to the wrong member.

This section defines the *semantics* of removing a device from an account. It is deliberately
about rules, not wire shapes: the concrete device-list and revocation message types are specified
separately in §7.1. What is fixed here is what any shape must mean, so that linking and revocation
are not designed independently and left to disagree.

### 8.1 Terminology

- **Linked device** — a device that has been paired into an account by the primary device
  (`PLAN.md` §4) and therefore holds its own per-device identity key and `DeviceAddress`.
- **Unlinking** — the user-initiated act of removing a device from their own account, performed
  from another device in that account (typically the primary). Unlinking is the *trigger*.
- **Revocation** — the security-relevant *effect* of unlinking: the removed device's identity key
  and `DeviceAddress` are marked invalid for the account, and peers must stop treating messages
  from or to that address as belonging to the account. Every unlink MUST produce a revocation;
  a revocation MUST NOT be assumed to happen on its own without an unlink (or an equivalent
  signed device-list update).

### 8.2 What revocation means

Revoking device `D` of account `A` MUST, once observed by a peer, mean all of the following:

1. `D`'s `DeviceAddress` is no longer a member of `A`'s device set.
2. New sessions MUST NOT be started to `D`; its `PreKeyBundle` MUST be removed from `A`'s
   `DiscoveryRecord` (§6) so senders cannot fetch it.
3. Existing sessions with `D` MUST be torn down; messages received from `D` after the revocation
   is observed MUST be rejected, not decrypted and surfaced to the application layer.
4. `D`'s Sealed Sender certificates (§5) MUST be rejected. Certificates are short-lived and bound
   to the device address, so revocation invalidates them at expiry at the latest; a peer that has
   already observed the revocation SHOULD reject them immediately rather than wait for expiry.
5. `D` MUST be excluded from fan-out: no further envelopes are addressed to it.

### 8.3 Who learns, and how

There is no server and no global switch, so revocation is a **signed, versioned, eventually
consistent** fact rather than an instantaneous one:

- The account's device set is carried as a **signed, monotonically versioned device list**. An
  update that removes `D` is signed by the primary device (the same signing authority that signs
  the `DiscoveryRecord` device set in §6) and published/forwarded to the account's remaining
  devices and to contacts.
- **Own devices** apply the update on receipt: they stop sending to `D`, tear down sessions with
  it, and refuse new sessions from it.
- **Contacts** learn of the revocation through the updated `DiscoveryRecord` (or an equivalent
  device-list update) and apply the same rules. Until a contact observes the update it may still
  accept messages from `D`; this window is inherent to a server-less design and is called out as
  residual risk in §8.5.
- **The revoked device itself** cannot be reached to be told. It retains its local history and
  keys and may keep attempting to send. Recipients that have processed the revocation reject it;
  recipients that have not, do not. Revocation is therefore best-effort and not a remote wipe.

### 8.4 Ordering, rollback, and re-linking

- Device-list updates are **monotonic**: a peer MUST reject an update whose version is not newer
  than the one it already holds. This is what stops a malicious relay or DHT peer from replaying
  a stale list to resurrect a revoked device (`docs/threat-model.md` §2, "Malicious DHT peer").
- A revoked device MUST NOT be re-added under the same identity key. Re-linking a device produces
  a **fresh identity key and a new device id**; the old address stays revoked permanently.
- Revocation of the primary device is out of scope for v0 and is an open item (§7): the primary
  holds the signing authority, so its loss is the "compromised primary device" adversary in
  `docs/threat-model.md` §2, not something this section can resolve.

### 8.5 Residual risk

- Revocation is **not instantaneous** and is **not enforceable** against a peer that never
  processes the update, or against a revoked device that simply keeps sending. It bounds the
  blast radius of a lost/stolen device (`docs/threat-model.md` §5.3) only for peers that have
  observed the update.
- A **compromised primary device** can sign a device list that keeps a rogue device in the
  account; the signature proves *who* signed, not that the signer is uncompromised
  (`docs/threat-model.md` §2).
- **Remote wipe is impossible** in a server-less design and is documented as a known limitation,
  not silently gapped (`docs/threat-model.md` §5.3).

## 6.1 Envelope-kind routing tag (out-of-band)

Both receive loops (the 1:1 direct session loop and the group sender-key loop) poll the same
relay mailbox, and the mailbox is destructive — a pickup removes the envelope. Without a
discriminator, whichever view is open destroys the other's mail. v0 therefore defines an
**envelope-kind routing tag** on the WS relay's store-and-forward ops
(`relay/src/ws.rs`, the browser-facing wire protocol):

- `send_envelope` carries an OPTIONAL `kind` field (`"direct"` | `"group"`) as a **sibling JSON
  field of the op** — never inside the ciphertext. `pickup_envelope` may carry the same field
  as a filter and echoes the tag of the delivered envelope.
- **The kind is ALLOW-LISTED.** Only `"direct"`, `"group"`, or an absent field is accepted on
  `send_envelope`; any other value is rejected with the distinct wire body
  `{"ok":false,"error":"InvalidKind"}` and the envelope is NOT queued. The check is the FIRST
  gate of the send arm — before the rate limiter and the PoW verifier — so an invalid kind
  fails fast: it consumes no challenge, burns no PoW-verification CPU, and changes no state.
  An unbounded, unvalidated tag would otherwise let a client grow the relay's kind map with
  arbitrary values.
- **The kind is NOT part of the ciphertext.** The envelope bytes are opaque, non-content
  payloads that pass through the relay byte-for-byte; the tag is routing metadata the relay
  stores and echoes verbatim without inspecting (or being able to inspect) the payload. No
  plaintext, key material, or content of any kind travels in the tag. This keeps the relay
  blind (§5, threat model "Honest-but-curious relay") while letting the two receive loops
  route before attempting a decrypt.
- **Fall-through policy (fail closed = not silently misrouted).** A missing or UNKNOWN kind is
  never silently skipped: it is delivered to the polling loop, which falls through to its own
  decrypt and fails closed there (tampered/corrupted warning) if the bytes do not verify. A
  known FOREIGN kind is not delivered to the wrong loop and is not destroyed by it: the relay
  leaves it queued (a filtered pickup reports `NotFound`) so the owning loop still receives it
  afterwards. The re-queue preserves the envelope's ORIGINAL expiry — it re-enqueues with the
  REMAINING lease, never a fresh TTL, so the wrong loop's repeated polls cannot keep a
  foreign envelope alive past its original expiry (and the per-recipient cap cannot be
  wedged shut by never-expiring foreign mail). An envelope already past its recorded expiry
  is dropped, and the relay prunes the kind map on the send and pickup paths so entries
  cannot accumulate without bound.
- A genuinely tampered envelope of the correct kind still fails closed with the existing
  tampered/corrupted warning — the tag changes routing, never verification.
- **The tag map is in-memory only.** The kind tags live in a relay-side in-memory map keyed
  by `(recipient_id, SHA-256 of the envelope bytes)`; the envelope ROWS persist in SQLite,
  but the tags do not. After a relay restart the map is empty, so every queued envelope is
  untagged and the `tag.is_none()` fallback delivers it to whichever loop polls first — the
  relay degrades to the pre-GRP-6 (unfiltered) behaviour until fresh sends re-tag their
  envelopes. This residual is accepted deliberately: rejecting untagged envelopes instead
  would re-queue them forever by every filtered poll and wedge ALL queued mail after a
  restart, which is strictly worse.
